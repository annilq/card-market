## cards 补 date_created / date_updated / user_created 系统字段（本回合）
- 需求：给 `cards` 加创建时间、更新时间、创建人三个字段。
- 实现：bootstrap.mjs 的 `cards` 集合声明增 3 字段，均带 Directus `special` 标记（语义标记）：
  - `date_created` timestamp, special=['date_created']
  - `date_updated` timestamp, special=['date_updated']
  - `user_created` **uuid**（关联 directus_users 的 UUID 主键，非 integer！），special=['user_created']
- **关键坑**：Directus 11.17.4 对「后期新增的 special 字段」**不会在 API 层自动写入**（实测新建卡牌三字段均 NULL）。故改用数据库层兜底，已固化进 bootstrap 的 `setupCardTimestamps()`：
  - `date_created`/`date_updated` 列 `SET DEFAULT now()`（插入自动取当前时间）
  - 更新触发器 `trg_cards_touch_updated`（仅刷新 `date_updated`，不含 TG_OP 判断——带 `TG_OP='INSERT'` 字面量的函数会报 "column INSERT does not exist" 解析错误）
- `user_created` 无可靠「当前用户」来源（API 层不自动填），保持可空；存量 6 卡牌已回填 admin 的 UUID；新建卡牌经 Directus 后台时亦不自动填（同属上述 special 不生效问题）。如需强制，需应用层在创建时显式写。
- 前端：`types.ts` Card 类型对齐为 `date_created/date_updated: string|null`、`user_created?: string|null`；`directus.ts` 的「最新上架」排序由临时 `-id` 改回语义正确的 `-date_created`（此前因字段缺失才用 -id 顶替，现已具备真实创建时间）。
- **顺手修一个既有 bug**：`getAnnouncement`（`directus.ts:171`）查 `announcements/1` 时请求了不存在的 `created_at,updated_at` → 公告详情页 403。announcements 集合本无这两字段，已从字段列表移除（详情页用 `published_at` 显示时间）。

## 后台体验修复：M2O 只能手输 ID + 后台英文界面（本回合）
- **现象**：Directus 后台编辑卡牌时，IP/系列/子系列/稀有度只能手输数字；后台全英文。
- **根因（两层叠加）**：
  1. `bootstrap.mjs` 的 M2O 字段用了 `interface: 'relational'`。`relational` 是 **display** 而非编辑接口，Directus 认不出 → 退化为纯文本输入。正确接口是 `select-dropdown-m2o`（配 `options.template='{{name}}'`）。
  2. 更关键：`ensureRelation` 用 `/relations?filter[collection][_eq]=...` 做幂等判断，但 **Directus 11 的 /relations 忽略 filter、总是返回全量** → 判断恒为"已存在" → **9 条 M2O 关系一条都没建**（DB 侧 `directus_relations` 对 cards/series/sub_series 为 0 行、`cards` 除主键无任何 FK）。没有 relation，即使 interface 对了也选不出数据。
- **修复**：
  - 字段声明全部补 `label`（中文名），`buildFieldMeta()` 统一生成 meta（interface/options/display/display_options/translations）。
  - 新增 `syncFieldMeta()`：存量环境也 PATCH 字段 meta，保证修正可落地（ensureField 遇已存在会 return）。
  - `ensureRelation` 改为直查 `directus_relations`（many_collection/many_field）判断，`on_delete` 必填用 NO ACTION、可空用 SET NULL；已补建 9 条关系。
  - `setupFileFieldTypes()`：`banners.image` / `site_settings.logo` 由 varchar 改 uuid（先 DROP DEFAULT 再 USING ::uuid，否则报 default cast 失败），从而能建 FK。
  - `cards.images`：`list` → `files` 接口（`type json` + `special:['files']` + `display:'files'`），后台可上传/多选，**API 读写形态不变**（仍是 id 字符串数组，已验证 PATCH + 匿名读）。
  - `date_created`/`date_updated` 设 `readonly: true`（DB 默认值 + 触发器维护，不该手改）。
  - `setupSettings()`：`default_language='zh-CN'`，并 PATCH `/users/me {language:'zh-CN'}`；结束时 `POST /utils/cache/clear`。
- **清理**：`directus_relations` 有 2 条指向不存在表 `cards_directus_files` 的孤儿关系（API DELETE 报 403），直接 DB 删除。
- **验证**：`/fields/cards` 四个关联字段 interface=select-dropdown-m2o 且 `schema.foreign_key_table` 正确；深层查询 `fields=ip_id.name` 可展开；默认 `fields=*` 仍返回标量 id（前端不受影响）；匿名读含关系/图片正常；prod:3000 与 dev:3001 六个路由全 200。

## 生产服务"反复静默退出"的真实原因（重要，勿再误判为代码崩溃）
- 现象：prod-server.mjs 多次以「无任何输出」失败（stderr 全空），表现为静默退出。
- 排查结论：**不是代码崩溃**，是被外部 `pkill -f prod-server.mjs` 终止（SIGTERM，所以 stderr 为空）。
  工作区里存在**另一个 WorkBuddy 会话（session 706a83e7-797e-4bee-96f6-c92cb2d700cf，非本会话 4837339e）**，
  它的 shell 正在执行 `pkill -f prod-server.mjs; sleep 1; node prod-server.mjs >/tmp/prod.log 2>&1`，
  即"杀掉旧进程 → 换新进程"。因此本会话每次重启都会被它 SIGTERM，表现为 task status=failed。
- 判别方法：`pgrep -fl prod-server.mjs` 会同时列出 node 进程和一个 `zsh -f -c ... pkill -f prod-server.mjs ...` 的 shell；
  看该 shell 的 `CODEBUDDY_SESSION_ID` 即可确认来自别的会话。
- 另一条教训：`EADDRINUSE` 时新进程会立刻退出，但端口上**已有**进程仍在正常服务 —— 重启前必须先用
  `lsof -nP -iTCP:3000 -sTCP:LISTEN` 确认端口真的空了，否则会误以为"服务挂了"。
- 顺带：带 HTTP_PROXY 的环境里，端口未监听时 curl 返回 502（代理包装了 connection refused），
  不是"服务在但上游异常"，排查一律加 `--noproxy '*'`。
- 已加固：prod-server.mjs 增加 server 'error' 日志、SIGTERM/SIGINT/SIGHUP/SIGQUIT 记录、uncaughtException/
  unhandledRejection 日志、exit 记录，以及可选心跳 `HEARTBEAT_MINUTES`（默认关闭）。

## 修复：按钮/链接“背景与文字不适配” + devtool 报错（本回合）
- **Bug 1（核心）：强调链接文字隐形**。「留言咨询」等 `<a class="bg-accent text-on-accent">` 文字变 `rgb(15,23,42)`（与背景同色）。
  根因：`styles.css` 里 `a { color: inherit; text-decoration: none }` 写在 **unlayered**（未包进 `@layer`）。
  Tailwind v4 中 unlayered CSS 优先级**高于** `@layer utilities`，于是覆盖了 `.text-on-accent` 工具类；
  `<button>` 无此全局规则所以正常，`<a>` 全军覆没。修复：把 `html,body`/`body`/`a` 基础规则全部包进 `@layer base`。
  **教训：Tailwind v4 自定义全局基础样式必须放 `@layer base`，否则会悄悄压过所有工具类。**
- **Bug 2：React 报 "Encountered a script tag while rendering React component" → 级联 "Hydration failed"（#418）**。
  根因：无闪烁脚本以 `<script dangerouslySetInnerHTML>` 直接写在 `__root.tsx` 的 JSX `<head>` 里，React 19 视为组件内渲染脚本。

  修复：改由 root route `head()` 返回 `scripts: [{ dangerouslySetInnerHTML: { __html: NO_FLASH_SCRIPT } }]`，经 `<HeadContent />` 渲染（TanStack Router 1.170 支持 head scripts），警告消失，脚本仍在首屏前执行。

## 前端界面多语言 i18n（本回合，决策记录）
- 语言：zh(默认)/ja/en。理由：后台已有 zh-CN+ja-JP 标签、店铺在东京、部署面向日/美。
- **URL 形态：可选路径段**，默认语言不带前缀（`/cards` 中文，`/ja/cards`、`/en/cards`）。未知语言段 404。
- 实测否决 `router.rewrite` 方案：`rewrite.input` 丢弃语言段后 `router.state.location.pathname` 只剩 `/cards`，
  在 `/ja/cards` 页面上 `buildLocation` 产出 `/cards/7`；且 `matchRoutes` 绕过 rewrite。语言状态无处安放是根因。
- 否决 cookie/localStorage 单存（不可分享、无 hreflang、SSR 无法按语言渲染）与根路径 302 到 `/zh`（多一跳、既有链接全失效）。
- 未引 i18next/paraglide：约 100 条文案、无复数/RTL 需求，编译插件或运行时库会加构建步骤与 hydration 边界，收益不抵成本。
- 文案：`src/lib/i18n/messages.ts`，`zh` 为唯一键来源，`MessageKey = keyof typeof zh`，`ja`/`en` 为
  `Record<MessageKey,string>` → 少翻/多写一条键都 typecheck 报错（不需要一致性脚本）。
- 运行时：`useLocale()` 从 pathname 首段派生，**无 Provider、无 locale state**（派生而非同步，SSR/客户端必然一致）；
  `useT()` 按 locale 缓存稳定引用；`formatDate` 固定 `Asia/Tokyo` 避免时区抖动。
- **两个实测坑（易复发）**：
  1) 裸 `<Link to="/message">` 会丢语言段 → 所有 `to` 必须带 `/{-$locale}` 前缀；语言段由当前路由**自动继承**，
     显式传 `params={{locale}}` 无效（不会让裸 to 长出语言段）。索引路由的 `to` 是 `'/{-$locale}'`，**无尾斜杠**（带斜杠是类型错误）。
  2) 语言切换器切到默认语言必须传 `locale: undefined`；传 `'zh'` 生成 `/zh/...` → 404（浏览器实测发现）。
- 后台内容里的站内路径（`banners.link` = `/cards?ip=1`）绕过路由类型，须经 `localizeHref()` 补前缀，
  否则从 `/ja` 点 banner 掉回中文（实测复现后修掉）。
- 边界：**不翻译 Directus 内容**（卡名/公告正文/店铺地址）。界面语言 ≠ 内容语言，内容多语言归 Directus 字段翻译。
- 验收：`scripts/check-i18n.mjs`（68 项断言：三语 SSR 文案、`<html lang>`、全部页面可达、未知段 404、hreflang、
  banner 补前缀、内容不被翻译）+ 真实 Chrome CDP 验证切换交互与零 hydration 错误。
- 文档：`docs/development.md` §7.2 + §11 清单、README「界面多语言」、ticket `.scratch/card-market/issues/10-frontend-i18n.md`。
- 未提交：工作区含此前未提交的深色主题改动（styles.css / 各 route 的 token 迁移），与本次 i18n 改动在同一批文件里交织，
  未做拆分提交（无法在不丢用户改动的前提下干净切分）。

## 后台「商品图片」报 relationship is not configured properly（M2M 元数据缺失）
- **现象**：后台卡牌编辑页 `商品图片` 下只有警告 `The relationship is not configured properly or you don't have permission to access it`，
  「新建/添加现有/上传」全消失；但**前台图片正常显示**、`/items/cards?fields=images.*` 与 `POST /items/cards_images` 全绿。
- **根因**：`directus_relations` 里 M2M 两条关系缺 `meta.junction_field`（bootstrap 的 `ensureM2M()` 早期只写了
  `one_field/one_deselect_action/sort_field`）。后台 `list-m2m` 的 `useRelationM2M()` 判定条件是
  `related_collection===集合 && one_field===字段 && **junction_field 非空**`，缺了就直接返回 undefined，
  模板落到 `v-else` 渲染 `$t('relationship_not_setup')`。**接口层不依赖该元数据**，所以 API 正常、只有后台界面坏。
- **判别方法**：`SELECT many_collection,many_field,one_field,junction_field,sort_field FROM directus_relations;`
  正常 M2M 应两条互指（`cards_id→directus_files_id` / `directus_files_id→cards_id`）。
  `/fields/cards` 看不出问题（type/special/interface 都是对的），**必须查 relations**。
  不是权限问题：本次 `/relations`、`/permissions` 全 200，无任何 403。
- **修复**：`ensureM2M()` 建关系时写 `junction_field`；新增 `ensureJunctionSide()` 做存量自愈（缺则 PATCH，齐则零写入）。
- **⚠ 大坑（真实踩到）**：`PATCH /relations` 的 `updateOne()` 是 **DROP 外键 → alterType → ADD 外键**，
  `on_delete` 只从请求体 `schema` 取。**漏传 schema 会把外键搞丢**（本次 `pg_constraint` 从 2 条剩 1 条，随后全丢）。
  所以修复时必须带 `schema:{on_delete:'NO ACTION'}`，并额外查 `pg_constraint` 校验外键、丢了补回。
- **验证**：置 NULL 复现 → bootstrap 修复 → 后台恢复（截图 `.scratch/card-market/evidence/m2m-{before,after}-fix.png`）；
  三场景（缺元数据/丢外键/两者全坏）均一次修好；连跑两次无输出=幂等；修完外键仍 2 条。
- 文档：`docs/development.md` §8 补「junction_field 是必需元数据」+「PATCH /relations 会丢外键」两条约定；
  ticket `.scratch/card-market/issues/11-m2m-images-relationship-warning.md`。
- 顺带（环境，非代码）：Directus 后台首次访问会弹「未设置项目所有者」不可关闭的 modal，挡住自动化点击。
  用 `PATCH /settings {project_owner, project_usage}` 置值即可关闭。
